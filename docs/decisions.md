# Decisions

- 2026-11-19: Scope is inventory + handover only; ordering and payments stay outside. Orders enter by CSV import of the Google Form.
- 2026-11-19: Supabase (Postgres, free) + static site on GitHub Pages. Firebase rejected: no Cloud Functions on Spark, so the change log could not be enforced; 50K reads/day cap.
- 2026-11-19: Roles are Main admin, Admin, Ops, IT. Ops sends the "come collect" mails.

## v1 build (2026-11-19)

- **Sign-in gate:** only emails on `members` (active, `@mdi.ac.in`, enforced by a check constraint) can sign in. A trigger on `auth.users` refuses sign-up for anyone else; RLS gives non-members zero rows. Main admins add anyone; IT adds/edits Ops and IT only; there must always be one active main admin.
- **Permissions live in Postgres.** RLS per table plus guard triggers: Ops may change only an item's status (any other column is refused); "handed over" can be set only with a live handover row; leaving "handed over" needs the handover undone first, which only admins can do and needs a reason. Handovers are never deleted. IT cannot change stock.
- **Audit log:** one `security definer` trigger on every app table writes who (from the JWT, with name and role from `members`), when, table, row, old/new JSON and changed columns. `audit_log` has no insert/update/delete grant for users and an append-only trigger that also stops the owner/service role. `item_id` is stored on each entry so per-shirt history is one indexed query.
- **Multi-row changes go through RPCs** (`set_items_status`, `record_handover`, `undo_handover`, `import_orders`), all `security invoker` so RLS still applies. They make bulk changes atomic and keep long id lists out of URLs.
- **Importer reads the form by position, not header text.** The 2026 form was edited while live, so shirts 2–4 are in either the old block ("Color ", "Color  2", "Color") or columns Google appended at the end ("T-shirt Details Color 2/3/4", "Batch 5/6/7"). Slots are found between "Add another T-shirt" columns; appended columns fill shirts 2–4 in order. Both layouts (and the later Reopening form) are covered by tests.
- **Duplicates:** same roll no. + same product + size + back name in a *different* response (or already in the tool) is held back for review. Two identical shirts in one response are treated as intentional. An exact re-import of a response (same timestamp, roll, slot) is skipped as "already imported", so re-importing the whole sheet is safe.
- **2026 form count:** the importer finds 1,008 shirts in 647 responses; the form's "Total" column sums to 1,011. The 3 extra are typos in three responses — amount paid matches the shirts found in each. The preview shows amount paid next to the expected price for every mismatch.
- **Custom sizes** (e.g. "Chest 38 / Length 28") are kept as typed and flagged, not rejected. Sizes outside a product's list (e.g. XXXS) are flagged too.
- **Form timestamps** are stored as India time (+05:30). D/M/Y vs M/D/Y is detected from the whole file.
- **Frontend data:** the app loads the whole round (≈1,100 shirts) once, paginating past Supabase's 1,000-row limit, and computes inventory/exports in the browser. It refreshes after every change and when the tab comes back into view. Fine at this size; revisit with views if a round passes ~10k shirts.
- **HashRouter** so deep links work on GitHub Pages without a 404 redirect trick. Google OAuth uses the PKCE flow.
- **Demo mode** (`npm run dev:demo`): an in-memory backend with made-up data and a role switcher, for trying the UI without accounts. Not included in the production bundle.
- **Tests:** `supabase/tests/db.test.ts` runs the real migrations in PGlite (in-memory Postgres) with a stand-in `auth` schema and checks every role limit and the audit trail.
- **Keep-awake:** a public `ping()` function (returns 'ok', reads nothing) is the only thing `anon` may call; a weekly GitHub Action calls it.
- **Call list default:** "Arrived, not collected" lists only students whose shirts are *all* in MART, so they come once; a toggle adds partly-arrived students. Emails copy comma-separated for Bcc; roll numbers copy one per line.
- **Ease of use for Ops comes first (Oliver, 2026-11-19).** Handover desk: no "Next" button; after a handover the desk shows a green "Done" line and goes straight back to an empty, focused search. Handover is three taps: student → "Hand over" → "<name> is taking it" (a friend's name + roll no. only if a friend collects). With one ready shirt there is no checkbox.
- **Receive stock tab** (Ops, admins): pick the colour → tick the shirts in the vendor's box (or "All M came") → "Mark as arrived". This is how stock gets into MART; the Shirts page bulk bar stays for admin corrections. Orders themselves still come only from the CSV import.
- **Three roles: Super admin, Admin, Ops** (Oliver, 2026-11-19). IT merged into Admin ("we'll maintain it anyway"). `main_admin` is labelled "Super admin" — Oliver for now — and can add, change and remove anyone.
- **Team & roles tab** is shown only to the super admin and admins. Admins can add admins/ops and change their roles but cannot create, edit or remove a super admin; only the super admin removes members. There must always be one active super admin. Enforced in RLS and tested.
- **First super admin** is seeded by migration `20261119120500_first_main_admin.sql` (`pgdm26oliver_j@mdi.ac.in`).
- **Phones:** checked at 360px with Android Chrome emulation; no page scrolls sideways. The login page warns when opened inside WhatsApp/Instagram etc., because Google blocks sign-in in those built-in browsers (https://developers.googleblog.com/2016/08/modernizing-oauth-interactions-in-native-apps.html).
- **"Item", not "shirt"** (Oliver, 2026-11-19): the next sale is hoodies, so every screen says item/items. Product names stay as entered.
- **Sales rounds hold the products.** A new sale (e.g. hoodies) = Products → New sales round → add its products; no code change. The sidebar always shows a labelled "Sales round" picker so it's clear which round every page, import and manual order uses.
- **Delete unused products** (admins): the Delete button is disabled when any order uses the product (the database refuses anyway via the foreign key). Products with orders are kept; close the round instead.
- **Manual orders** (admins, Oliver 2026-11-19): "Add orders → One order by hand" for orders outside the Google Form. Saved through the same `import_orders` RPC as CSV, so it is atomic and logged; Activity shows "added an order by hand". It recognises an existing roll number and warns when the same item already exists for that student.
- **GitHub Pages on a private repo needs a paid plan** (https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages). Left to Oliver: upgrade or make the repo public.
- **Names come from Google, with an optional nickname** (Oliver, 2026-11-19): an admin can set a nickname on Team & roles; when set it is shown everywhere, including new activity-log entries, otherwise the Google name is used. `members.display_name` is set from the Google account at first sign-in and refreshed on every sign-in (`link_my_member`); the Team page no longer has a name box, and edits only change role/active. Before someone's first sign-in the list shows the part of their email before the @ and "Not signed in yet". Past activity-log entries keep the name that was current when they were written (the log is append-only).
- **Phone layout, simpler** (Oliver, 2026-11-19): bottom bar = the everyday jobs, **Home · Hand over · Receive · Lists · More**, the same for every role (Items, Inventory, Print list, Add orders, Activity, Products, Team are under More). The top bar shows the sales round as a tap-to-change chip instead of repeating the page title. Tab rows wrap instead of hiding options off-screen; Inventory shows one card per product on phones; every page opens at the top. "Exports" is now called "Student lists".
- **Roles & permissions are data** (Oliver, 2026-11-19): tables `roles`, `permissions`, `role_permissions`; every RLS policy and RPC checks `has_perm(...)`. The super admin role always has everything and can't be edited or deleted. The super admin can create, rename and delete roles (a role with members can't be deleted) and tick permissions on the "Roles & permissions" tab. Action ticks are enforced by the database; page ticks only hide pages in the app (team members can still read stock data). Replaces the fixed `app_role` enum.
- **Locked sales rounds** (Oliver, 2026-11-19): `campaigns.locked`. Only a super admin locks/unlocks. A locked round is hidden from everyone else in the database (its products, items, handovers, notes, imports, spare stock and activity entries; students whose only orders are in locked rounds) and frozen for everyone, super admins included, until unlocked.
- **Excel uploads** (Oliver, 2026-11-19): Add orders accepts .csv, .xlsx, .xls and .ods, read in the browser with SheetJS 0.20.3 (installed from cdn.sheetjs.com; the npm-registry copy is outdated and has a known advisory). With several tabs, the first tab that has a roll-number column is used and a picker lets you change it. Rows without a timestamp are no longer matched as "already imported" by slot.
- **Sample file**: "Download sample file" builds an .xlsx in the browser in the Google Form layout, with the current round's real product names and a "How to fill" tab (tested to import cleanly).
- **Vendor print list picking** (Oliver, 2026-11-19): tick single orders or a whole size; Copy, CSV, Print and "Mark as sent" then use only the ticked ones (nothing ticked = whole list). Unticked ones are left out of the printout.
- **Load one round at a time** (2026-11-19, for the free plan's 5 GB/month egress, https://supabase.com/pricing): the app downloads only the selected round's items, students and handovers (plus the small shared tables). After a handover, receive, bulk status change or "mark as sent" it re-fetches only the changed items instead of everything. Adding an order by hand looks up a student from older rounds on demand.
- **Backups** (2026-11-19): the free plan has no automatic backups (same source). Super admins get "Download full backup" on Products: one Excel file with every table, all rounds and the change log. Do it monthly into the MART Google Drive; it contains student contact details, so never on GitHub or personal drives.
- **Backup super admins** (Oliver, 2026-11-20): 2-3 personal (non-@mdi.ac.in) Google accounts can be kept as super admins in case the MDI accounts are ever lost. Enforced in the database (migration `20261120120000_backup_super_admins.sql`): a non-MDI email is allowed only on a super admin row and can't be moved to another role (remove it instead); the rows, log entries about them and anything they do are visible to super admins only. No change for other users. Use 2-step verification on those Gmails and don't use them day to day.
- **Payments check** (Oliver, 2026-11-20): payment details from the order form (paid to whose QR, amount, transaction ID, screenshot link) are saved per form response in `payments` (migration `20261120130000_payments.sql`). Members use personal UPI QR codes, so statements can't be imported; instead people with "Check payments" tick each one Received or Problem (logged with who and when). It is a separate verification step and never blocks handovers or changes stock. Flags: student total differs from items cost, same transaction ID twice, ID used in another round, no ID, no payment on record. Re-uploading an old order file saves just its payment details (matched by roll number and form time, to the second). New permissions "Payments" (page) and "Check payments" start with the super admin only. Excel shows 12-digit UPI IDs as 5.1E+11; the importer reads the full number.
- **Own order form, replacing the Google Form + Sheets** (Oliver, 2026-11-23): a separate site in its own repo, writing into the same Supabase project; students sign in with @mdi.ac.in Google and see only their own orders; MART Orders stays team-only. This brings ordering into scope (taking money still stays outside: students pay by UPI, we record it). Plan and open decisions: `docs/order-form-plan.md`.
- **Order form database** (Oliver confirmed 2026-11-23; migrations `20261123120000_student_signup.sql`, `…120100_order_form.sql`, `…120200_order_form_storage.sql`):
  - **Sign-up:** any @mdi.ac.in account may now sign up (students). Non-MDI emails still need an active `members` row (backup super admins). MART Orders data still needs an active `members` row, so a student gets zero rows from every MART table (tested table by table).
  - **Students get no table rights.** They use three `security definer` functions that check the caller and validate every value: `get_order_form()`, `submit_order()`, `my_orders()`. They only count as a student when signed in **with Google** (`app_metadata.provider`), so an email/password sign-up can't pose as an @mdi.ac.in student. Keep the Email provider off in Supabase Auth anyway.
  - **Students cannot edit or cancel an order** (Oliver). There is no function for it; MART admins fix orders in MART Orders as before.
  - **Form admins** are a separate list, `form_admins`, of **at most 2** emails (enforced). Only a MART super admin adds or removes them. Form admins open/close a round (one open at a time), show/hide products, set descriptions, photos and whether a custom size is allowed, and upload/rotate payment QRs. **The form never edits MART data** (Oliver, 2026-11-23): prices, sizes and names are read-only on the form and changed only in MART Orders; `form_admin_save_product` refuses them (tested). A form admin who is not on the MART team still sees nothing in MART Orders.
  - **Max 6 items per order** (Oliver): `form_rounds.item_cap` (1–6, default 6); `order_items.source_slot` now allows 1–6.
  - **submit_order** saves, in one transaction: the buyer (by roll number), one `order_items` row per item (`form_order_id` set, `source_timestamp` = submit time, slot 1–6), a `payments` row (amount = sum of database prices; `paid_to` = the QR's payee; screenshot as a Storage path in `payments.screenshot_path`) and a `form_orders` row. Items and payments are audited like everything else, with the student's email as the actor. A roll number already linked to another account (or imported with a different email) is refused ("contact MART"); one account can't order under two roll numbers. The same UPI transaction ID can't be used twice. Name on the back: letters, spaces, `. ' -`, max 12 (`form_rounds.name_max`), saved in capitals — vendor rules still to confirm. Batch/course/section/print-batch must be from the round's lists.
  - **QR rotation:** exactly one live QR; after switching, orders started on the old QR are still accepted for 2 hours. Each order records its QR (`form_orders.qr_id`).
  - **My orders** shows form orders and older imported orders whose buyer email is the student's Google email (or whose buyer row is linked to their account). Locked rounds are hidden, as in MART Orders.
  - **Storage:** private buckets. `payment-screenshots` (1 MB, images): students upload only into `<their user id>/`, read only their own; "Check payments" reads all. `form-assets` (3 MB, images; QRs and product photos): any signed-in user reads, form admins write. The MART Payments page opens form screenshots through a 10-minute signed link.
  - **Screenshot storage budget** (2026-11-23): the free plan has 1 GB file storage and 5 GB egress per month shared by database and storage, per organization (https://supabase.com/pricing, https://supabase.com/docs/guides/platform/manage-your-usage/egress). One screenshot per order, shrunk to ~200 KB on the phone (1 MB hard cap per file). A round like 2026 (647 form responses) ≈ 130 MB, so about 7 rounds fit; worst case (every file at the 1 MB cap) ≈ 650 MB per round. Revisit before the 4th round: delete screenshots of rounds whose payments are all checked, after a backup.
